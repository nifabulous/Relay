## Summary

Relay has no front door: `GET /` redirects into the app. This spec adds a public landing page at `/`
that explains what Relay teaches and shows it working. It also introduces the visual language the app
adopts in later phases.

The look borrows firecrawl.dev's structural grammar: hairline rails fixed to the container for the full
page, full-bleed section rules, faint cells, crosshair markers and bracketed mono labels. It pairs that
with Stripe's way of using colour: navy ink, cool tinted surfaces, primary-tinted hairlines and one
saturated primary. The signature object is a dot-matrix globe drawn from the Atlas's own map topology.
It tours corridors one after another and turns under the pointer. The page ships in light, dark and
black.

## Governing invariants

Every acceptance criterion below is checked against these, not in isolation.

1. **Truth.**
   - Every fact about Relay on the page comes from repository data, either generated by the facts export
     at build time or imported from the frontend's own data modules. That covers counts, scheme names,
     speeds, limits, module titles, corridors and the tool counts (verdicts, watchlist entries, holiday
     calendars, settlement lags, STP rules). Nothing is hand-typed, except the corridor city
     coordinates, which live in one reviewed table with a test (see Data sources).
   - Demonstration values are allowed: the GBP 25,000 payment, its timestamps, the example IBAN, the
     sample SSI record, the MT103, the payee names and the tool examples. They live in one reviewed
     file, `src/landing/render/demo.json` (typed by `demo.ts`), and the page presents each one as
     fictional or illustrative. Every demonstration value that claims a computed result (a checksum, a
     verdict, a fee, a value date, a screening score, a status code) is asserted by
     `tests/test_landing_demo_claims.py`, which reads the same file and runs the real Relay code.
   - Every link points at something that exists. There is no "Sign in", because Relay has no learner
     accounts.
2. **Simulation is always stated.**
   - The SIMULATION marker is visible in the hero, in every payment-shaped section (01, 02, 04, 06) and in
     the footer.
   - Demonstration payments use only fictional institutions: Harborline Bank, Meridian Clearing and
     Northstar Bank.
   - Real bank names never appear on the landing page.
   - Every account number shown is an `ACCT-` placeholder.
3. **Flag off means today, exactly.**
   - With `RELAY_LANDING_ENABLED` unset or false (fail-closed `_env_flag` semantics: only `1`, `true`,
     `yes` or `on` enable it), `GET /` returns the same 302 it returns today: to `/app`, or to `/learn`
     when the build is absent.
   - No landing file is mounted, read or served on any path.
   - The `/app` build config, entry and output are byte-identical to today.
   - The only new work is reading the flag: once at process start (`mount_landing()` in
     `app/landing.py`, called from `app/main.py`), and once in the build command, which then skips the
     landing build. With the flag off, `root()` checks one module-level value, `LANDING_HTML`, which is
     `None`, and then runs today's code.
4. **Containment.** At 390, 768, 1024 and 1440px, no element overflows its bordered box and the page
   never scrolls horizontally.
5. **Motion only enhances.**
   - All content is present in the built HTML.
   - Every animated element shows its final state when JavaScript is disabled, when
     `prefers-reduced-motion: reduce` is set, or when a stored `reducedMotion: true` is present.
   - Anything that starts by itself and moves for more than 5 seconds has a pause control (WCAG 2.2.2).
6. **The preference is shared, and never corrupted.**
   - The page reads `theme` and `reducedMotion` from the app's `relay:preferences` record and paints the
     right theme before first paint.
   - A write re-reads storage at the moment of the click. It merges only `theme` into a valid
     schemaVersion 1 record, or writes the complete default record when nothing is stored.
   - It never adds, removes or repairs other fields. It never overwrites a record that is corrupt, is not
     an object, or has another `schemaVersion`.
   - When storage throws, the theme changes for the current page only.
   - Every text pair passes AA in all three themes.

## Architecture

### Build and serving

```text
frontend/
  vite.config.ts                 unchanged (the /app build)
  vite.landing.config.ts         new: base "/landing/", publicDir false, input landing.html,
                                 outDir ../app/landing_dist; renders the sections at build time
  landing.html                   new entry: pre-paint theme script (a byte-for-byte copy of
                                 index.html's), motion flags, head metadata, font preloads
  src/landing/
    render/                      build time only: sections (React), facts.ts (zod contract),
                                 demo.json + demo.ts, content.ts, facts.fixture.json (for tests)
    client/                      ships to the browser: enhancers, styles/tokens.css, styles/landing.css
    brand/relay-symbol.svg       favicon (the Route Loop symbol)
    generated/                   gitignored: facts.json, globe-points.json
  scripts/
    build-landing.mjs            facts export, globe points, landing build, checks
    build-landing-if-enabled.mjs the Vercel build hook
    build-globe-points.mjs       globe point set
    check-landing-build.mjs      budgets, no source maps, no /app or secret references
    check-landing-boundary.mjs   import rules
app/
  landing.py                     mount_landing(), landing_response()
  landing_dist/                  build output (gitignored)
  data/landing_corridors.py      the reviewed corridor table
scripts/
  export_landing_facts.py        facts export (Python)
```

- **Separate build.** The landing page is built by its own Vite run, `npm run build:landing`, with its own
  config. The `/app` config is not edited. A two-entry build would make Vite emit a shared
  `modulepreload-polyfill` (or `preload-helper`) chunk referenced from both HTML files; the review
  reproduced this with the repo's Vite 8.2.1. The separate run cannot do that. The landing config uses
  Vite 8 names: `build.rolldownOptions.input`, and `runnerImport` for the build-time render.
  - `publicDir: false`, so nothing from `frontend/public/` is copied into the landing output.
  - The canonical link carries `vite-ignore`; without it Vite tries to bundle `href="/"` and fails.
  - The output file is `app/landing_dist/landing.html`, named after the entry.
- **`/app` stays byte-identical.** `build-landing.mjs` hashes `app/static/relay` before and after and
  fails if anything changed. Measured on 2026-10-02: the `/app` output hash is the same with the landing
  sources absent, present, and after a landing build. Tailwind's `source(none)` in `global.css` keeps
  the landing files out of its class scan.
- **Output outside `app/static`.** `app/static` is mounted wholesale at `/static` (`app/main.py:123`).
  Building the landing page into `app/landing_dist/` means no flag state can expose it through that mount.
- **Serving.** `app/landing.py` reads the flag once, when `app/main.py` calls `mount_landing(app)` at
  import, using `_env_flag` from `app/config.py` (fail-closed: `1`, `true`, `yes`, `on`).
  - **Flag off:** `mount_landing` returns `None` without touching the filesystem, nothing is mounted, and
    `root()` runs today's code.
  - **Flag on, and both `landing.html` and `assets/` exist:** mount `/landing/assets` with
    `Cache-Control: public, max-age=31536000, immutable` on successful responses, and make `root()`
    return the landing HTML with `Cache-Control: no-cache`. The app-wide security headers still apply.
  - **Flag on, build missing:** nothing is mounted and `root()` falls through to today's redirect.
  - **Restart rule:** changing the flag takes effect on the next deploy or process start.
- **Deploy.**
  - `vercel.json` `buildCommand` becomes
    `cd frontend && npm run build && node scripts/build-landing-if-enabled.mjs`. The hook exits 0 after
    reading the flag when it is off, using the same true spellings as `_env_flag`. When the flag is on,
    it runs `build-landing.mjs`, and any failure fails the deploy.
  - Two checks pin the build command by exact equality and change with it:
    `tests/tutor/test_config.py:271` and `scripts/verify_tutor_release.py:65`.
  - Python is already present in the Vercel build (`installCommand` runs `pip install '.[ai]'`).
    `build-landing.mjs` picks the first of `RELAY_PYTHON`, the repo's `.venv`, `python3` and `python`
    that can import the app's dependencies.
  - `functions."app/main.py".excludeFiles` does not exclude `app/landing_dist/**`; a test pins that.
  - `RELAY_LANDING_ENABLED` is set per Vercel environment and documented in `.env.example` and the README.

### Static-first rendering

Sections are React components rendered to static markup at build time with
`react-dom/server.renderToStaticMarkup` through Vite's `runnerImport`, in production mode. No React
runtime ships to the landing page.

- **Facts are read, not imported.** `tsc` checks all of `src/`, so a static import of the gitignored
  `generated/facts.json` would break the `/app` build on every clean checkout. The Vite plugin reads the
  file with `fs`, and `renderLanding()` validates it against the zod contract in `render/facts.ts`
  (strict objects, so unknown or renamed keys fail the build).
- **What the renderer may import:** `curriculum.ts`, `practice/questionBank.ts`,
  `practice/selectDaily.ts` (for `DRILL_SIZE`) and `cases/caseCatalog.ts` (with its type-only
  `caseTypes.ts`). None of them imports CSS, touches `window`, reads `import.meta.env` or loads Sentry.
  `labRegistry.tsx` is excluded: it lazy-loads every lab, and the labs import 25 CSS files. The lab
  count comes from `CURRICULUM` instead, which `labRegistry.test.ts` keeps one-to-one with the registry.
- **What the client may import:** only `src/landing/client/`, the generated point set as a URL, and the
  Geist `@fontsource` stylesheets. `scripts/check-landing-boundary.mjs` enforces both lists and the purity
  of the allowed data modules, and CI runs it next to the Base UI boundary.

| Enhancer (`src/landing/client/`) | Responsibility |
|---|---|
| `globe.ts` (with `globe-math.ts`) | Canvas globe, drag, corridor tour, pause control, legend link |
| `scroll-route.ts` | Route stage and vertical stepper progress |
| `anatomy.ts` | Plate stack progress and ledger |
| `rails-tabs.ts` | WAI-ARIA tabs over pre-rendered panels |
| `iban-demo.ts` | IBAN groups and checks lighting in sequence, once, with Replay |
| `counters.ts` | One-time count-up of stat values on an `aria-hidden` overlay |
| `theme-control.ts` (with `preferences.ts`) | Footer theme control: System, Light, Dark, Black |

Each enhancer does nothing when its elements are missing. The mobile menu needs no enhancer: it is a
`<details>` disclosure, so it works without JavaScript.

**No layout shift, and final states without motion.** A second inline script in `landing.html`, after the
theme script, adds `js` to `<html>`, and adds `motion` unless `prefers-reduced-motion: reduce` or a stored
`reducedMotion: true` asks otherwise. The stylesheet keys off both classes:

- Rails panels other than the first are hidden only under `.js` and until the tabs enhancer takes over,
  so nothing collapses after load. Without JavaScript every panel shows and the tab list is hidden.
- Without `.motion`, every animated element is styled in its end state: the route drawn, every hop and
  plate active, the IBAN and its checks lit. The enhancers then do nothing.
- Without `.js`, the globe stage and the theme control are hidden; the corridor legend stays.

### Themes

- **Tokens.** The landing stylesheet defines the light, dark and black token sets from DESIGN.md
  (**Dark and black themes**), with the app's selectors:
  `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) }` and
  `:root[data-theme="dark"]`. The black block, `:root[data-theme="black"]`, is self-contained: it
  repeats every dark token it uses, so it renders correctly when the OS is set to light. Every colour
  lives in `client/styles/tokens.css`; `landing.css` contains no hex, and a test enforces both.
- **Pre-paint.** `landing.html`'s first inline script is a byte-for-byte copy of `index.html`'s: same
  storage key, same `schemaVersion` guard, same accepted values. `theme.test.ts` already executes the
  `index.html` copy against `applyTheme()` (`theme.test.ts:206-319`). It is extended to assert the copy is
  identical and to run the same matrix against `landing.html`.
- **Writer.** Client code cannot import `lib/persistence/storage.ts` (boundary rule), so
  `client/preferences.ts` carries a minimal writer that follows invariant 6, and
  `client/theme-control.ts` applies the theme exactly as the app's `applyTheme()` does (a parity test
  compares them for every theme and OS setting). A vitest suite round-trips the writer's output through
  the app's `loadPreferences()`, pins its default record to `defaultPreferences`, and covers these cases:
  - merge into a full v1 record;
  - merge into a v1 record missing fields (they stay missing);
  - fresh write equals `defaultPreferences` with the chosen theme;
  - a record with another `schemaVersion`, corrupt JSON or non-object JSON is left untouched;
  - `getItem` or `setItem` throwing changes the theme for the page only;
  - storage is re-read at click time, not taken from the record seen at load.
- **Cross-tab limitation.** The app's shell keeps an in-memory snapshot and has no `storage` listener
  (`AppShell.tsx:31-37`, `:60-64`). A theme chosen on `/` while `/app` is open in another tab is overwritten by that
  tab's next preference write. "Carries over" therefore holds across page loads, not between open tabs.
  Fixing the app's listener is out of scope.
- **Canvas.** `globe.ts` reads its colours from CSS custom properties (`--gDot`, `--gGrat`, `--gLimb`,
  `--gPlate`, `--gInk`, `--gPacket`, `--c1`…`--c8`). It re-reads them on a `relay:theme` event and on an OS
  appearance change while the preference is `system`. Without motion it draws a frame only when
  something changes: a theme change, a drag, or a legend selection. (The prototype stopped drawing during a
  drag under reduced motion; the build fixes that.)

| Corridors on the globe | `app/data/landing_corridors.py` | same export (cities, coordinates and source kind only; no BICs) |
| Module titles and count, lab count, practice questions and drill size, cases | `curriculum.ts`, `questionBank.ts`, `selectDaily.ts`, `caseCatalog.ts` | imported by the build-time renderer |

| Demonstration values | `src/landing/render/demo.json` | imported by the renderer; read by the claims test |

Values from `origin/main` on 2026-10-02, for scale only (the page always shows the export's): 761 banks in
152 countries, 12,196 SSI rows (5,636 with settlement fields), 763 beneficiary banks, 1,167 correspondents,
156 Atlas beneficiary countries, 29 corridors over 72 rule rows, 10 currencies with 34 domestic schemes
plus SWIFT gpi, 7 verdicts, 15 watchlist entries, 10 holiday calendars, T+0 to T+2, and 14 STP rules.

- **The facts export** seeds an isolated in-memory SQLite database (`StaticPool`) with the app's own seed
  code, then queries it. It never opens `config.DATABASE_URL`, whatever that points at; a test sets it to
  an unreachable Postgres URL and the export still succeeds. Importing the app still builds the default
  engine, but SQLAlchemy connects lazily and the export never uses it. Numbers on the page therefore
  describe the reference data shipped at the deployed commit, and the page says so. The export resolves
  `app` from its own checkout, so a shared editable install cannot point it at another worktree. It takes
  about 2.5 seconds.
- **Facts are not committed.** Nothing has to be regenerated when SSI ledgers change, and no PR can fail
  because a count moved. Tests pin the behaviour instead:
  - the export is deterministic (two runs are byte-equal);
  - its counts equal direct queries on the same seeded session;
  - its shape equals the committed fixture `src/landing/render/facts.fixture.json`, which the render
    tests use and the zod contract accepts. Python output, fixture and contract therefore cannot drift
    apart unnoticed.
- **`stp_checker.RULES`** lists the 14 rules `check_stp` runs, each with the finding code it emits. A test
  checks it against the checker's source: every emitted code belongs to exactly one rule, the rule numbers
  match the rule-block comments, and the module, `check_stp` and API docstrings state the registered count.
  `check_stp` itself is unchanged.
- **`landing_corridors.py`** holds eight entries. Each has a currency code, origin and destination city,
  country, latitude and longitude, and a source: a case (id and its `corridorLabel`), or a corridor-rule
  key (currency, destination country, intermediary BIC). A pytest checks:
  - each corridor-rule key exists in `CORRIDOR_RULES`, and the intermediary's city and country in `BANKS`
    match the arc's origin;
  - each case id appears in `caseCatalog.ts` with a matching `corridorLabel`, for example
    "United Kingdom → Germany";
  - currency codes are unique, coordinates are in range, and there are no more than eight entries (one per
    colour slot).

  The four case corridors are GBP Lagos → London, USD Toronto → New York, EUR London → Frankfurt and MXN
  New York → Mexico City. The four rule corridors are KES, INR, JPY and AUD from New York, keyed on the
  corridor rules whose intermediary sits there. The legend labels each "case desk" or "corridor rule" and
  never names the bank. The table is the only hand-typed factual data, and the test above is its review.
- **Demonstration claims.** `tests/test_landing_demo_claims.py` runs each claim through the real code:
  - **IBAN:** `validate_iban` accepts it with country GB; schwifty's `IBAN` gives check digits 82, bank
    WEST, sort code 123456 and length 22.
  - **Payee:** `match_names("Jon Okafor Ltd", "Jonathan Okafor Limited")` is a close match. (The
    prototype's "John Okafor Limited" scores 0.973, a full match, so it could not show a close match.)
  - **Prepare:** `decide()` for a valid instruction with a close-match payee gives
    PROCEED_WITH_CAUTION, REVIEW and STOP at lenient, standard and strict.
  - **Fees:** `simulate_fees` for GBP 25,000 through one correspondent gives 25,000.00 received under OUR
    (the sender adds 10.00), 24,990.00 under SHA and 24,965.00 under BEN.
  - **Screening:** `screen_payment` clears Harborline Bank, Meridian Clearing and Northstar Bank, with
    best watchlist scores of 0.42, 0.64 and 0.45. (The prototype's "possible hit" on Meridian was false.)
  - **Value date:** CAD over EFT, sent at 18:00 on Monday 29 June 2026, misses the 17:00 cut-off, trades
    on 30 June, skips the 1 July holiday and settles on 2 July at T+1. (The prototype's 30 September
    holiday is not in the CAD calendar, and its 14:15 ET cut-off is not in the code.)
  - **MT103:** `check_stp` returns CLEAN with no findings, with `date.today()` pinned to the demonstration
    as-of date, 2026-10-01. Rule 11 reads today's date (`stp_checker.py:310-311`), so an unpinned run
    would change the verdict the next day. The message carries a UETR, so all 14 rules pass, not 13 plus
    an info finding.
  - **Tracking:** each status shown maps to its pacs.002 code through `iso_transaction_status`.
  - The demo accounts are `ACCT-` placeholders and the institutions are the three fictional ones. None
    of the three names appears in any seed bank or SSI record.
- **Seed on main.** A fresh seed succeeds on `origin/main`. The failure the first review traced was on the
  later, unmerged commits of `feat/correspondent-atlas`, so it does not block this work. The prototype's
  numbers (703 banks, 8,510 SSI routes, 145 Atlas countries) came from that branch.

## Interaction and motion

### Globe

- **Rendering.** Orthographic projection on a canvas. Land points are depth-shaded in seven alpha buckets.
  A 30° graticule in the hairline colour and a hairline limb circle. DPR capped at 2. Paused when off
  screen (IntersectionObserver).
- **Pointer (mouse and pen).** Drag rotates longitude (x) and latitude (y), with latitude clamped to ±75°.
  Release keeps inertia, decaying by 0.93 per frame.
- **Touch.** `touch-action: pan-y` on the globe. Vertical swipes scroll the page, so the globe never traps
  scrolling. Horizontal swipes rotate longitude.
- **Tour.** Corridors play in order. Each gets 1.3s of camera travel to the arc midpoint, 1.7s of draw
  with a packet at the head, and 1.1s of hold. Finished arcs remain as trails whose opacity falls with
  age, to a floor of 0.16. A drag suspends the tour, which resumes after 3.5s idle.
- **Pause control (WCAG 2.2.2).** A visible, keyboard-reachable **Pause tour** / **Play tour** button,
  labelled with its current action. Paused stays paused for the rest of the page view, through drags and
  idle time. Focusing a legend button also pauses the tour.
- **Keyboard.** Dragging is a pointer enhancement. Keyboard users get the same result through the legend:
  each legend button flies the globe to its corridor. No information is reachable only by dragging.
- **Labels.** The active corridor labels both endpoints. When the endpoints are within 150px on screen,
  one combined label is drawn instead. Text uses the heading token on a surface-coloured plate, with a
  colour swatch beside it. Text is never drawn in, or on, the series colour.
- **Legend.** One cell per corridor: swatch, currency code, city pair and source. Each cell is a
  `<button>`.
  The active cell changes its surface and shows a 2px top bar in the corridor colour, so the active state
  is never shown by colour alone.
- **Reduced motion.** No sway, no tour and no inertia; every corridor is drawn statically. Drag still
  works, and a legend button turns the globe to its corridor.

### Route (section 01)

- **Desktop stage (>980px).** A 456px stage holds the SVG path along the grid lines. Progress is
  `clamp((0.8·vh − top) / (1.05·height))`. The dash offset and the packet follow progress, and each node and
  tag activates as progress passes its distance fraction. Tags for hops not yet reached use the muted
  token.
- **Small screens (≤980px).** An ordered list with a 3px rail, filled to a `--p` custom property.
- **Containment.** Tags have a fixed 260px width and fixed positions, and the containment audit asserts
  both.

### Anatomy (section 02)

The cube's y position maps to section progress. Plates and ledger rows activate at their y thresholds.
Upcoming rows use the muted token.

### Rails tabs (section 03)

- **Pattern.** WAI-ARIA tabs with automatic activation and a roving tabindex.
- **Keys.** Left and Right move and select, wrapping at the ends. Home and End jump to the first and last
  tab.
- **Wiring.** Each tab carries `aria-controls`, and each panel carries `aria-labelledby`. Panels are
  pre-rendered and toggled with `hidden`.
- **Colour.** No categorical colour on the tabs (DESIGN.md). The selected tab shows an accent bar and a
  surface change.

### Counters and IBAN

- **Counters.** They count up once on first view, over 1.1s with an ease-out. The real value stays in the
  accessibility tree; only an `aria-hidden` overlay animates. Reduced motion shows the final value.
- **IBAN.** The example `GB82 WEST 1234 5698 7654 32` lights group by group, then shows its checks. It
  plays once when scrolled into view, then shows a **Replay** button. The label reads "watch it validate":
  there is no input field.

## Responsive behaviour

| Width | Rails | Type | Layout |
|---|---|---|---|
| ≥1400px | Container and outer frame | H1 60/64, H2 52/56 | Full layout; legend in 8 cells |
| 981–1399px | Container only | as above | Legend in 2 rows of 4 below 1160px |
| 641–980px | Container only | H1 48/52, H2 40/44 | Nav collapses to a `<details>` menu; heads stack; 3-column grids stack; route stepper; anatomy and rails panels stack |
| ≤640px | Container at 12px gutters | H1 38/42, H2 32/36 | Single-column grids; legend 2×4; full-width CTAs; globe stage 1:0.82; plate sub-labels hidden, names enlarged |

**Rail geometry.** Container rails sit at `calc(50% ± min(var(--cw), 100% − 2·var(--g)) / 2)`, the same
formula as `.wrap`, so they stay on the content edges at every width. A rail fixed at `50% ± 540px` would
leave the screen below 1112px (review finding 17). Outer rails sit at `calc(50% ± var(--ow) / 2)` and
show only at 1400px and wider.

Primary touch targets are at least 44px. Controls stay at 16px or more on mobile. Safe-area insets apply
to the sticky nav.

## Accessibility

- **Globe.** The canvas is `aria-hidden`, and the legend is its text equivalent.
- **Route and plates.** The route stage SVG is `aria-hidden`; the stepper and tag text carry the content.
  The anatomy SVG is decorative beside the ledger, which carries the same steps.
- **Contrast.** All text pairs meet WCAG 2.2 AA in light, dark and black (tables in DESIGN.md). Amber and
  teal sit below 3:1 on white, so every corridor carries a text label; their dark steps clear 3:1.
- **No opacity states.** Pending and inactive text uses the muted token, never reduced opacity.
- **Status.** Always text plus colour.
- **Moving content.** The globe tour is pausable. The route and plates follow the scroll. The IBAN demo and
  the counters play once.
- **Focus and structure.**
  - Focus: a 2px outline in the accent token (primary 600 in light, 400 in dark and black) with a 2px
    offset.
  - Landmarks: header, nav, main, footer. Headings in order.
  - Skip link to `main`.

|---|---|
| Landing JavaScript, all seven enhancers | ≤ 25KB gzip, excluding globe points; no React runtime. Measured 5.2KB |

| LCP element | The hero heading, never the canvas |
| CLS | ≤ 0.05 |

The `/app` bundle budget (`bundleBudget.test.ts`, `scripts/check-bundle.mjs`, 210KiB) is unaffected
because the `/app` build is unchanged. `scripts/check-landing-build.mjs` checks the landing output after
every landing build. Budgets are measured with Node's default `zlib.gzipSync`. The point set is generated
in 2.7 seconds: a bounding-box prefilter keeps the exact spherical test to one or two polygons per point
(the naive version took 134 seconds, with byte-identical output).

## Rollout and rollback

The page is additive and gated by `RELAY_LANDING_ENABLED`, which defaults to off in every environment.
Turning the flag off and redeploying restores today's redirect and removes the landing mount; there is
no data or schema to unwind. The only persistent state the page writes is the theme, stored in
`relay:preferences` in the app's own format (invariant 6), so a rollback leaves nothing the app cannot
read. Geist is scoped to the landing build; the app's typography is untouched until Phase 3.
